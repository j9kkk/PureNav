# PureNav 核心功能模块梳理

> 状态：v0.10.0 已按「A 全能自托管收藏夹管理器」方向落地，见 §六
> 出发点：一个自托管的**收藏夹管理器 + 导航入口**——把浏览器里越积越乱的几百条书签收进来，用多级目录树、点击热度、防重收录与体检治理重新组织，同时保留「打开就有快感」的门户视图。

---

## 一、同类产品对标

| 产品 | 形态 | 组织方式 | 配置方式 | 动画/视觉 | 权限 | 明显短板 |
| --- | --- | --- | --- | --- | --- | --- |
| **Dashy** | 自托管仪表盘 | 多页面 → 区块(section) → 条目(item) | YAML，可在 UI 内编辑 | 主题/自定义 CSS 强，动效普通 | 可选认证、多用户、OIDC/SSO、细粒度权限 | 配置心智重，YAML 字段多，普通用户上手难 |
| **Homepage** | 自托管仪表盘 | 分组 → 服务卡片 | YAML + Docker label 自动发现 | 偏克制、信息密度高 | OIDC / 简单密码，默认假设在网络边界内 | 依赖大量第三方集成，纯导航场景偏重 |
| **Homarr** | 自托管仪表盘 | 拖拽网格 → 应用 | 全图形化，数据库存储 | 拖拽体验好，视觉中等 | 内置用户/角色/分组、OIDC/LDAP | 集成与 widget 生态重，部署依赖多（DB/Redis） |
| **Heimdall** | 自托管启动页 | 应用卡片，可按分类 | 图形化 + SQLite | 朴素 | **无内置认证**，靠反向代理 | 功能简单，无细粒度组织与检索 |
| **Sun-Panel** | 自托管导航 | 分组 → 站点 | 全可视化零配置，无外部数据库 | 较精致，支持自定义 JS/CSS | 多账号隔离、内外网切换 | 生态与开放性弱于 Dashy/Homarr |
| **WebStackPage** | 导航站模板 | 分类 → 链接 | 静态数据，需自配后端 | 传统门户式，无动效 | 由各后端自实现 | 只是模板，前后台需自己拼 |
| **iTab 类新标签页** | 浏览器扩展/网页 | 分组 → 卡片 | 账号同步 | **动效与视觉是其核心卖点** | 账号体系、云同步 | 闭源、数据在第三方、不可自托管 |
| **Raindrop / linkding** | 书签管理器 | 集合/标签 | 图形化 | 弱（列表为主） | 多用户、共享、访客 | 偏"稍后读/收藏"，不是"入口页" |

### 结论：给自己的位置

- **Dashy / Homarr / Sun-Panel** 是直接竞品，功能覆盖度已经很高，但都以"仪表盘"为核心，信息密度大、配置重。
- **iTab 类**证明了"分组 + 卡片 + 动效"这个方向对普通用户有强吸引力，但它是闭源、数据托管在第三方。
- **Raindrop / linkding** 说明"收藏/检索"是另一条路径，不是入口页诉求。

因此 PureNav 的差异化不应是"再做一个功能更全的仪表盘"，而应是：

1. **轻**：只管"入口"，不做容器监控、不做 100+ 服务集成；
2. **好看且顺手**：动画质量是一等公民，而不是主题包的副产品；
3. **好管**：后台是纯图形化 CRUD，不要求用户写 YAML；
4. **数据自持**：单机可部署，导出即可带走。

## 二、功能模块拆分

按"前台 / 后台 / 服务端 / 非功能"四层拆，每层给出模块、要点和优先级。

### A. 前台（展示层）

| 模块 | 内容 | 优先级 |
| --- | --- | --- |
| **A1 布局与渲染** | 分组 → 卡片 → 图标三级渲染；自适应网格；分组可折叠/展开；空态与骨架屏 | P0 |
| **A2 导航跳转** | 站内/新标签打开；点击反馈；外链标识；协议白名单（http/https） | P0 |
| **A3 即时检索** | 按名称/域名/拼音/标签本地过滤；`/` 聚焦；上下键选择；回车打开；搜索引擎切换 | P0 |
| **A4 动画系统** | 入场 stagger、hover 抬升、点击按压、分组切换、视图过渡；统一动效 token（时长/曲线）；遵循 `prefers-reduced-motion` | P0（差异化核心） |
| **A5 视图切换** | 卡片 / 紧凑列表 / 极简模式；密度调节 | P1 |
| **A6 视觉定制** | 深浅色、主题色、壁纸/渐变、卡片圆角与阴影、图标风格 | P1 |
| **A7 内网优先** | 同一站点配置内外网地址，访问时按可达性自动选择（纯前端探测，见风险 R3） | P1 |
| **A8 个性化组件** | 时钟、天气、搜索框、公告条（作为可选插槽，不塞进 v1） | P2 |
| **A9 可访问性** | 键盘全流程可用、焦点可见、对比度达标、动效可关闭 | P1 |
| **A10 离线/降级** | 配置快照缓存、图标懒加载与失败回退、弱网可用 | P2 |

### B. 后台（管理层）

| 模块 | 内容 | 优先级 |
| --- | --- | --- |
| **B1 认证** | 管理员登录；密码哈希（bcrypt/argon2）；会话或 JWT；登录失败限流；改密；登出 | P0 |
| **B2 分组管理** | 增删改查、排序（拖拽）、备注、分组图标、启停 | P0 |
| **B3 导航项管理** | 增删改查、URL、标题、描述、图标、标签、置顶/权重、启停、批量操作 | P0 |
| **B4 拖拽排序** | 组内排序 + 跨组移动；与前台顺序一致（单一数据源） | P1 |
| **B5 图标处理** | 手填 URL、本地/对象存储上传、Iconify 搜索、自动抓取 favicon；统一回退链 | P1 |
| **B6 站点设置** | 标题、Logo、Favicon、默认主题与布局、页脚、SEO/分享卡 | P1 |
| **B7 导入导出** | JSON 全量导出/导入；浏览器书签 HTML 导入 | P1 |
| **B8 变更记录** | 最近操作日志，便于误删恢复定位 | P2 |
| **B9 权限模型** | v1：单管理员；预留 role 字段，后续支持多用户/只读访客/分享密码 | P2（设计上先预留） |

### C. 服务端与数据层

| 模块 | 内容 | 优先级 |
| --- | --- | --- |
| **C1 数据模型** | `Group`、`Item`、`Tag`（可选）、`Setting`、`User`、`Session`、`AuditLog`；排序用显式 `order` 字段而非数组下标 | P0 |
| **C2 API 分层** | 前台只读接口（可缓存）+ 后台受保护写接口；统一错误格式与参数校验 | P0 |
| **C3 缓存与快照** | 前台配置整包快照 + ETag/版本号；写操作后失效 | P1 |
| **C4 图标代理** | 服务端抓取 favicon / 转存，带 SSRF 防护、超时、内容类型与大小校验 | P1 |
| **C5 存储** | 上传图标落本地目录或 S3 兼容存储，可配置 | P1 |
| **C6 站点健康探测** | 可选：定时探测地址可达性并在卡片上标记（需严格限制目标与频率） | P2 |

### D. 非功能与工程约束

| 维度 | 硬要求 |
| --- | --- |
| **安全** | 全部外链协议白名单；URL 渲染做 XSS 转义；后台 CSRF/Origin 校验；CSP；登录与写接口限流；不向前台接口下发内网地址（见 R3）；不做未净化的自定义 JS/CSS（或明确标注为高风险开关） |
| **性能** | 首屏 LCP 优先于动效；动画只走 `transform`/`opacity`，保持 60fps；图标懒加载与尺寸约束防 CLS；列表 stagger 设上限，避免长列表"逐个飞入" |
| **可访问性** | 键盘可达、焦点可见、语义化结构、`prefers-reduced-motion` 一键降级 |
| **部署** | Docker 单镜像；SQLite 默认、Postgres 可选；全部配置走环境变量；启动即迁移 |
| **可观测** | 结构化日志、`/healthz`、版本号端点 |
| **国际化** | 文案集中管理，v1 中英双语文案可后补 |

## 三、MVP 边界（建议）

**做**：分组 CRUD 与排序、卡片 CRUD 与图标、前台网格渲染、即时检索、新标签跳转、管理员登录、深浅色、响应式、Docker 部署、SQLite 持久化、JSON 导出。

**暂时不做**：服务集成/widget 生态、容器状态、多用户与 RBAC、自定义 JS、浏览器扩展、云同步、站点存活探测。

这条边界的理由：竞品的"重"恰恰来自集成生态，而 PureNav 的胜负手在"打开就有快感 + 后台三分钟录完一屏"。

## 四、关键风险与设计决策（需在动手前定下来）

**R1 动画 vs 首屏性能**——高保真动画最容易反噬。建议先定义动效规范（时长 120/200/320ms 三档、标准缓动、stagger 单组上限 8 项、首屏动画延迟不超过 300ms），并把它落成可复用的 token 与包装组件，而不是每个页面手写。同时提供"减少动效"开关。

**R2 图标来源不一致**——手填 URL + 上传 + Iconify + 自动抓取会得到四种视觉权重。建议统一为"一个图标管线 + 固定回退链"（自传 → Iconify → favicon → 文字首字母色块），并在后台预览中强制同尺寸裁切。

**R3 内网地址泄露**——内外网双地址是很实用的功能，但若后台把内网地址一并下发给公开的前台接口，等于把内部拓扑暴露给任何访问者。建议：内网地址只在前台本地探测使用、不进入可公开缓存的接口返回；或由访问来源/IP 段服务端裁剪。

**R4 SSRF**——自动抓 favicon、健康探测都是"服务端去请求用户填的 URL"，必须限制内网段、限制协议、限制重定向与响应大小。

**R5 权限模型预留**——v1 只有单管理员，但 `User` 表应直接带上 `role`，`Item`/`Group` 预留 `owner_id`/`visibility`。否则后续加"分享给访客""多人协作"要动数据迁移。

**R6 排序持久化**——不要用数组下标表达顺序（并发/拖拽易错乱），用稀疏 `order`（如 1024 步长）或 `(group_id, order)` 唯一约束 + 批量重排。

## 六、v0.10.0 实际落地：从"门户"转向"收藏夹管理器"

上面 §二 的模块拆分仍然有效，但优先级重排过。原因是原方向只解决"24 个固定站点怎么摆得好看"，真实用户的痛点在**收藏夹规模与生命周期**上：几百条书签滚不到底、单条目子分类独占一行留白洞、改名换目录必须切去 `/admin` 填表格、收录要手填四个字段、没有点击热度也就没有"哪个才是我真正常用的"、重复与死链无从发现。

### 6.1 已实现（对应 §二 模块号）

| 能力 | 实现位置 | 对应模块 |
| --- | --- | --- |
| **三区一浮层工作台**：固定 `100vh`，左 `248px` 智能视图 + 多级文件夹树 + 标签筛选，右顶栏搜索/排序/视图切换，底部状态栏 | `apps/web/src/pages/NavPage.tsx`、`apps/web/src/nav-workspace.css` | A1 A5 A9 |
| **子文件夹药丸横排**：点父目录时子目录渲染成顶部的紧凑药丸，书签汇入双列流，消灭"单条目子分组独占整行"的留白洞 | `.nx-subfolder-card` | A1 |
| **四个智能视图**：全部 / 常用置顶 / 最近访问（按 `last_visited_at`）/ 待整理收件箱，均跨文件夹聚合 | `NavPage.tsx` 的 `ViewKind` | A3 |

| **拖拽归档**：书签卡片拖到侧栏树节点或子文件夹药丸即完成移动，落点有高亮反馈 | `NavPage.tsx` `dropProps` | B4 |
| **书签体检中心**：健康分 + 重复网址 / 死链 / 永久重定向分类清单，支持重新扫描全库（150 条 / 6 并发）与逐条修复 | `GET /admin/items/doctor`、`POST /admin/items/doctor/scan` | C6 |
| **多级书签树无损导入**：解析 Netscape HTML 的文件夹路径，按 `parent_id` 逐级建真实树，服务端 `backfillGroupTree` 兜底旧导出格式 | `apps/web/src/lib/bookmarkParser.ts`、`settings.ts` | B7 |

### 6.2 相比 §二 的取舍变化

- **A4 动画系统降级为克制**：工作台是高频的生产力界面，动效只保留 150ms 的底色/边框过渡，不做入场 stagger 与卡片微光。
- **B9 多用户仍未做**：单管理员 + 未登录只读浏览；写操作全部需要会话。
- **A8 个性化组件不做**：时钟、天气、公告条砍掉，状态栏只显示真实数据（条数、置顶、收件箱、体检异常数），不做伪造的在线延迟这类噪音。
- **C6 站点健康探测升级为 P2→P1**：它是"体检中心"的数据来源，必须有；但严格限定目标（SSRF 防护复用图标抓取那套 `resolveAndGuardHost`/`requestWithHostGuard`）、并发与每次扫描条数。
